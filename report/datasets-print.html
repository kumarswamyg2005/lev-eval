Phase 2 datasets

Which second exploitation catalogue to use, and the four reasons the obvious choice does not work as shipped. Supersedes the 5 September version, which contained an error that would have produced a silent failure in the estimator.

Companion to LEV-calibration-Phase1.pdf  ·  machine-readable version in DATASETS.md  ·  prompt in RESEARCH-PROMPT.md

VulnCheck KEV is a superset of CISA KEV, not an independent list.

Their documentation: “encompasses all vulnerabilities listed in the CISA KEV catalog, plus approximately 80% more.” Lincoln–Petersen on the pair as downloaded gives m = |L1| by construction and collapses to |L2|. The arithmetic runs and returns a plausible number — the worst kind of bug. It is still the right source, but only after the filter in §1.

Correction 1

Constructing an independent list from VulnCheck

The schema exposes provenance per report, so a CISA-free list L2' can be built rather than assumed. cisa_date_added is the marker of contamination, not a convenient join.

1Drop cisa_date_added entirely.
2Filter vulncheck_reported_exploitation[] to reports whose URL host is not cisa.gov / www.cisa.gov.
3Keep a CVE only if a report survives step 2, or reported_exploited_by_vulncheck_canaries == true.
4First-observation date = min(date_added) over surviving reports.

The canaries flag is VulnCheck’s own honeypot telemetry, structurally independent of CISA. That subset alone is a defensible L2 if the URL filter draws reviewer objections. Document the filter in the paper — it is a methodological contribution in its own right, and no prior work does it.

Correction 2

Four sources measure the wrong quantity

Exploit-DB, Metasploit, Nuclei and AttackerKB record exploit availability, or analyst assessment of it — not exploitation in the wild. A CVE with a Metasploit module and no observed attack traffic is a capture in that list and a non-capture in CISA KEV, so including it estimates “CVEs with public tooling”: a different and much larger population.

Exclude all four as capture lists. Keep them as covariates. A CVE with a public PoC is more likely to be captured by every list, which is exactly the dependence the model has to absorb. This is an estimand objection, not an access one.

Correction 3

Circularity with EPSS — and it reaches Phase 1

EPSS’s exploitation labels come from Fortinet, AlienVault, Shadowserver and GreyNoise (Jacobs et al., arXiv:2302.14172). LEV is computed from EPSS, so validating LEV against GreyNoise or Shadowserver is partly circular.

Worse, and this hits work already done. CISA KEV is an input feature to EPSS v3 — “Public vulnerability lists (3 features): CISA KEV, Google Project Zero, Trend Micro ZDI.” Phase 1 therefore compared a predictor that has the outcome baked into it. Measured in analysis/leakage.py with two designs that cannot select on the outcome:

TestResult
EPSS across the listing date, net of non-KEV controls with the same starting score (1,168 CVEs; pairs straddling a retraining excluded) median ×1.00; upper quartile ≥ ×2.85
LEV before CISA listed them (220 KEV members with a pre-listing history, median 2.8 months)15% at LEV ≥ 0.5; median 0.005, against 1.0 afterwards

The leak is real for a sizeable minority of listed CVEs, not all of them. The larger finding is that high LEV among KEV members is mostly a consequence of listing, not a forecast of it — which bears directly on CSWP 41’s proposal to use LEV to find exploited CVEs missing from KEV.

Withdrawn. An earlier version of this page reported over-confidence rising from 11.9× to 32.7× on a “leak-free” cohort, and a compressed discrimination range there. That cohort was built by deleting KEV members only, keeping every non-member, so the observed rate fell by construction. Both results are withdrawn.

Correction 4

Independence is violated everywhere — model it, do not assume it

Every catalogue in this space reads the same vendor advisories and the same security blogs. Naive two-source Lincoln–Petersen assumes independent capture and will be rejected in review.

Log-linear MSEInteraction terms across ≥ 3 lists, so positive list dependence is a fitted parameter rather than an assumption.
StratificationBy vendor tier and disclosure year. Phase 1 already measured capture probability varying 14× by vendor; pooling gives the classic downward-biased estimate.
Chao lower boundRobustness check — consistent under unmodelled heterogeneity, and gives a defensible floor.

A third list is what makes the log-linear approach possible at all.
